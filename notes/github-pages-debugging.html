NOTE 013 // GITHUB PAGES / DEBUG

GitHub Pages debugging

When the repository is correct but the public page seems determined to display yesterday's JavaScript.

01

Confirm the commit exists

Open the repository and verify the intended file actually contains the new code on the branch used by Pages.

02

Wait for deployment

GitHub Pages is not always instant. Give the deployment time to finish before debugging code that has not reached the site yet.

03

Hard refresh

Reload without relying on the browser's cached copy. This is especially important after changing CSS or JavaScript while keeping the same filenames.

04

Use cache-busting when needed

<link rel="stylesheet" href="style.css?v=1.2.1">
<script src="script.js?v=1.2.1"></script>

Changing the query version makes the browser request a fresh asset while keeping the real filename unchanged. This fixed stale-script behavior in our published games.

05

Open DevTools

Check Console for JavaScript errors and Network for missing files or stale responses. A button that “does nothing” is often either old JS, a runtime error or an event handler that never attached.

06

Check relative paths

Project Pages lives under /repository-name/. Prefer relative file paths so assets continue working there instead of accidentally pointing at the domain root.

Debug order

  • Correct commit?
  • Pages deployment finished?
  • Hard refresh.
  • Cache-bust assets.
  • Console errors.
  • Network / missing files.
  • Relative paths.
