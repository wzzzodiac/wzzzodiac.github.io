NOTE 015 // ROS 2 / DEBUG

ROS 2 quick checks

The diagnostic order that proved useful when a driver or node looked alive but the actual data path was not.

01

List nodes

ros2 node list

Confirms which ROS 2 nodes are currently participating in the graph. A missing driver or processing node is visible immediately.

02

List topics and types

ros2 topic list -t

Shows available topics together with their message types. Useful for catching wrong names or an unexpected message format.

03

Inspect one message

ros2 topic echo <topic> --once

Prints one received message and exits. This answers the basic question: are messages actually arriving?

04

Measure frequency

ros2 topic hz <topic>

Measures the observed publishing rate. A topic can exist without delivering a stable stream, so this check matters.

05

Then check the consumer

If the source topic is healthy, confirm the processing node is subscribed to the exact topic/type and that its output topics exist. Only after that use RViz.

06

RViz-specific lesson

Topic discovery alone does not prove transport compatibility. In the BA setup, IPC namespace differences prevented point-cloud transport between containers, and later a QoS reliability mismatch blocked processed topics.

Data-path order

  • Can the sensor/device be reached?
  • Does the driver start?
  • Does the source topic exist?
  • Does one message arrive?
  • Is frequency stable?
  • Does the processing node exist?
  • Do processed topics exist?
  • Can RViz consume them?
